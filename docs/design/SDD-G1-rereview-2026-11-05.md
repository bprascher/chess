## 3. Answers to the specific questions

### (a) Does the snapshot express refused moves and held clocks without a new field

**Verdict: SUPPORTED** by the documents, with the supporting sentence missing from the app SDD. Adding it is a **text clarification of an existing field (G1)**, not a new field. No escalation to Brian is triggered.

Evidence:

1. The snapshot carries `clocks`, `state` and `allowed_actions` [OBS architecture.md:820; OBS app:993].
2. `allowed_actions` is `ActionKind[]`, a list that the domain computes per context and front-ends render from, so refusal is expressed by leaving kinds out [OBS architecture.md:721; app:993; domain:350 area, 3.11.5 table].
3. `Game::view` returns `GameView { state, ply, turn, plies, clocks: ClockSync, allowed_actions, outcome, eco }` [OBS domain IFP-DOM-2, line 367], and `ClockSync = { white_ms, black_ms, running_side: Option<Side>, as_of }` [OBS domain:372]. The snapshot lists the same field names. This is the strongest fact and neither the architect's evidence table nor OQ-APP-016 cites it.
4. Clients receive `{white_ms, black_ms, running_side, as_of}`, and `running_side = None` when stopped [OBS architecture.md:602; app:872].
5. The UI already takes `running: Side | null` from a `GameSnapshot` and treats null as stopped [OBS ui:363]. The CLI stores `running_side` from "any event carrying clocks" [OBS cli:446].

What the documents do not do is say that `GameSnapshot.clocks` is the domain `ClockSync` (nothing in the app SDD names `GameView`). That is why OQ-APP-016 (a) calls the fact inferred, and it is a gap in text, not in the design.

**Sentence the app SDD must add** (DD-APP-03, shape rules, replacing the `[UNV]` sentence; wording is the author's to adjust): "`GameSnapshot.clocks` has the type of the domain `ClockSync` (`{white_ms, black_ms, running_side: Option<Side>, as_of}`, domain IFP-DOM-2 `GameView.clocks`); `running_side` is null when the clocks are stopped, and the untimed shape is <as decided for FND-RR2-02>." Then OQ-APP-016 (a) closes.

Only if the software engineer decides the snapshot should carry a clock type that lacks `running_side`, or the design adds any field, does the D-89 escalation clause fire (G2, Brian). Nothing in the text proposes that.

### (b) Soundness of the `[Rewind]`-or-empty rule and the signature test

- **Against domain Policy:** sound. D-89 changes neither `Policy::check` nor `Policy::allowed_actions`; the builder reduces the list (D-89 (3); app:861). The `Rewind` rule (h-h or h-c in progress; refused for c-c) gives `[Rewind]` for human games and empty for computer-against-computer, exactly as the app SDD says. See FND-RR2-07 for the two sentences elsewhere that this makes untrue outside the degraded state.
- **Against D-80:** consistent. D-80 refuses every append, clock change and engine start; `Rewind` is a client-side view of plies the snapshot already holds; `Detach` and `Shutdown` are session messages, not kinds `[INF, domain 3.11.5 has none]`. D-80 itself lists no kinds, and the app SDD says so (app:863).
- **Against DD-UI-015 "Analysis screen stays available":** conflict, FND-RR2-05. Minor.
- **Signature test:** sound and discriminating (no non-degraded in-progress context can be within `{Rewind}`; a paused or draw-offered timed game lists other actions, UT-UI-015 (iv)). Weakness is ownership and coupling to OQ-APP-016 (b), FND-RR2-04.
- **OQ-APP-016 scoping:** (b) is correctly an open Minor and does not block v1.0: the worst outcome is that a degraded Training game offers or hides an analysis entry. It must close before the CLI and UI reducers are coded, because it changes signature (c). (a) is not a Minor question; it is the escalation test. It is cheaply closable with the sentence in (a), after which only (b) remains. Recommend splitting the row so the G2 possibility and the minor question have separate owners and states. The row's gate cell ("G1, G2 for (a) if a field is needed") is accurate as written.

### (c) Order independence and publish order against D-65, D-80, D-82, steps 4, 5a and 5b

- **D-89 order** (apply prefix, hand to store applier, set state, publish snapshot, reply `JournalWriteFailed`, then re-check) agrees with step 5a item 3 and with step 5b ("What the session publishes on entry is the entry rule of step 5a") [OBS 2081, app:863, app:865]. The store hand-off before publication keeps RR-A-3 and FIND-R23-010. No contradiction with D-65 part 2, D-80 (re-check is the only append) or D-82 (poisoned writer: entry with no adopted fact, re-check cannot append; step 4 at app:854 cross-refers correctly).
- **Reply versus snapshot:** they travel on different paths, so the front-end must not depend on arrival order. The new rule evaluates on either arrival, and cases (i) and (vi) test both orders. Sound, with the two exposures FND-RR2-06 (false `Degraded`) and the transient `Failed` message ("you can try the move again") that shows between a reply that arrives first and the snapshot. The second is harmless but unlisted.
- **Re-check ending the game:** the one real gap, FND-RR2-01.
- **Lag path:** the session serialises snapshot building in its mailbox, so a lag snapshot cannot be older than the entry snapshot while carrying a higher `seq` `[INF]`. No finding.
- **No subscriber at entry:** nothing is sent, and a later subscriber's first snapshot carries the projection (D-89 (4); UT-APP-28 (b), (g)). Consistent.
